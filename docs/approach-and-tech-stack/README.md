# Why This Approach and Tech Stack

## Product approach

Borrower Copilot is designed as a borrower-side decision-support tool rather than a lender approval workflow.

The product starts with the borrower's situation and asks:

- What can this borrower safely carry each month?
- What might a lender consider?
- What rate range deserves scrutiny?
- What should the borrower ask before accepting an offer?

This leads to a deliberate separation:

```text
Likely lender range != safe borrower range
```

A lender may be willing to offer more than the borrower should accept. Showing both ranges makes that distinction visible instead of hiding it behind one maximum loan amount.

## Why deterministic rules

The financial outputs are generated by deterministic TypeScript functions rather than an AI or machine-learning credit model.

This approach was chosen because:

- The same inputs should produce the same result.
- Every material output needs an explainable reason.
- The prototype does not have a bureau dataset or lender underwriting dataset.
- Borrowers should be able to inspect the assumptions behind affordability, rates, collateral, and stress tests.
- Unit tests can verify formulas and edge cases directly.

The rules engine is separated from the UI. The UI collects answers and presents results; it does not calculate affordability or silently invent missing values.

## Why ranges instead of single numbers

Loan pricing and eligibility depend on information that this prototype does not have, including lender policy, bureau history, documentation quality, property acceptability, and current offers.

The application therefore returns ranges for:

- likely lender amount
- safe borrower amount
- fair rate
- estimated all-in APR

Unknown information is represented explicitly with `null`. It is not converted to a poor credit score, zero income, or an optimistic assumption.

## Why adaptive questions

Showing every possible question to every borrower would make the assessment longer and less relevant.

The questionnaire starts with a small set of must-questions and then adds follow-ups based on answers:

- Salaried borrowers receive employment, savings, expense, and quote questions.
- Self-employed and business borrowers receive income-range, documented-income, collateral, and productive-use questions.
- Informal and gig-income borrowers receive volatility, existing-debt, bounce, savings, and productive-use questions.

This keeps the flow focused while still collecting information that can materially change an output.

## Technology choices

### Next.js App Router

Next.js provides the route structure for the landing page, assessment, results, and Negotiation Card. The App Router keeps each user-facing stage addressable and makes the application easy to build and run with the existing project setup.

The prototype uses static route rendering where possible and a small client-side layer only where interaction or browser session state is required.

### React

React is used for the interactive assessment flow and result/card views. The assessment needs local state for:

- current question
- entered answers
- adaptive question list
- validation feedback
- navigation between questions

### TypeScript

TypeScript gives the borrower profile, question definitions, evaluator result, product assumptions, and validation issues explicit contracts.

That matters here because the system has many optional values. A typed contract makes it harder to accidentally treat an unknown value as a real numeric value.

### CSS and Tailwind import

The project keeps the existing Tailwind CSS setup but uses a focused CSS design layer in `app/globals.css`. This gives the prototype:

- responsive desktop and mobile layouts
- explicit color variables
- consistent result states
- print styles for the Negotiation Card
- a distinctive visual language without introducing a large component library

### Vitest

Vitest provides fast tests for the pure engine and questionnaire modules. The test suite covers:

- Priya, Ravi, and Anita walkthrough directions
- adaptive question routing
- unknown credit handling
- zero-income behavior
- invalid input validation
- repayment stress
- collateral and product routing

### Browser session storage

The completed borrower profile is passed from the assessment to the results and Negotiation Card routes through `sessionStorage`.

This was chosen for the v1 prototype because it allows a multi-page experience without adding a backend, authentication, database, or persistent personal-data storage.

## Repository boundaries

The main boundaries are:

```text
app/          routes and page composition
components/   interactive and presentational UI
lib/engine/   deterministic financial calculations
lib/questions/ adaptive question definitions and routing
data/        centralized assumptions
types/        shared TypeScript contracts
tests/        engine and questionnaire verification
docs/         product rules, walkthroughs, and decisions
```

Keeping those boundaries explicit makes it possible to replace the prototype assumptions later without rewriting the UI.

## What this approach optimizes for

This approach optimizes for:

- explainability
- deterministic behavior
- borrower comprehension
- quick iteration
- low infrastructure cost
- testable financial logic

It does not optimize for production underwriting accuracy or lender-specific approval prediction. Those require data and integrations outside the scope of this prototype.
